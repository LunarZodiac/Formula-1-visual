# Публикация атласа

## Целевая схема

- Vercel размещает приложение Next.js
- Supabase размещает PostgreSQL/PostGIS
- локальная PostgreSQL остаётся средой разработки и подготовки данных
- JSON и GeoJSON остаются проверенными read-моделями для первого публичного запуска
- импорт, аудит и экспорт выполняются отдельной задачей, а не внутри Vercel Build

## Окружения

До публичного запуска используются два независимых облачных окружения:

1. Preview: Vercel Preview и отдельный Supabase staging-проект
2. Production: production deployment и отдельный Supabase production-проект

Preview не должен получать пароль или service-role ключ production-базы.

## Подготовка Supabase

1. Создать staging-проект
2. Включить PostGIS в схеме `extensions`
3. Применить миграции `database/migrations` по порядку
4. Применить необходимые seed-файлы или повторно выполнить импорт
5. Запустить проверки из `scripts`
6. Сравнить число сущностей и геометрию с локальной базой
7. Только после проверки повторить процесс для production

Прямое подключение PostgreSQL используется для миграций, импорта и дампов.
Серверные функции в будущем должны использовать пулер Supabase. Пароль базы и
service-role ключ нельзя передавать в клиентский код.

Схема `atlas` остаётся внутренней. Если frontend потребуется живой доступ к
данным, для него создаётся отдельная схема `api` с ограниченными представлениями,
функциями, правами и RLS-политиками.

## Подготовка Vercel

1. Импортировать Git-репозиторий в Vercel
2. Установить Root Directory: `apps/web`
3. Framework Preset: Next.js
4. Install Command: `pnpm install --frozen-lockfile`
5. Build Command: `pnpm build`
6. Не указывать Output Directory — Next.js adapter определит её автоматически
7. Добавить только необходимые переменные окружения
8. Проверить Preview deployment до подключения production-домена

На текущем статическом этапе приложению не требуется пароль базы. Публичные
переменные Supabase добавляются только после появления функций, которые их
используют.

## Порядок публикации изменений

1. Изменить код, миграции или данные локально
2. Запустить аудиты данных
3. Обновить JSON/GeoJSON read-модели
4. Выполнить `pnpm lint` и `pnpm build` в `apps/web`
5. Создать коммит
6. Отправить ветку в GitHub и проверить Vercel Preview
7. Применить миграции к staging до проверки функций, зависящих от базы
8. После приёмки объединить изменения в основную ветку

Импорт исторических данных не должен запускаться автоматически на каждом деплое:
это отдельный контролируемый процесс с журналом запуска и проверкой качества.
