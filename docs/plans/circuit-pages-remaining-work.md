# «География скорости» — единый план развития

Обновлено: 5 сентября 2026

Цель продукта: картографическая система для пространственного, исторического и статистического исследования Formula 1. Каждая крупная функция должна объяснять, где произошло событие, как объект менялся со временем, чем объекты отличаются географически или как результаты распределены по карте.

## Текущая архитектурная база

- Веб-интерфейс использует React 19 и API Next.js App Router через Vinext 1/Vite 8. Текущий серверный runtime и сборка ориентированы на Cloudflare Workers
- Карты и 3D работают в браузере через MapLibre GL и Three.js
- Отдельного прикладного backend/API сейчас нет. Node.js-скрипты импортируют, проверяют и экспортируют данные вне пользовательского запроса
- PostgreSQL/PostGIS в схеме `atlas` является источником истины. Интерфейс читает опубликованные JSON/GeoJSON-снимки из `apps/web/public/data`, поэтому пароль базы и прямой доступ к ней браузеру не нужны
- В репозитории находятся 17 последовательных миграций, отдельные seed-файлы и собственный журнал `public.atlas_schema_migrations`
- Избранное пока хранится локально в браузере; аккаунтов и синхронизации пользовательских данных нет

## Этап 0. Стабилизация и облачный стенд

Этот этап выполняется до следующего продуктового спринта. Переход runtime нельзя
совмещать с исправлением карт, данных и интерфейса в одном большом изменении.

1. Зафиксировать отмену предыдущего перехода отдельным понятным коммитом после проверки diff, чтобы репозиторий не оставался в промежуточном состоянии поверх уже опубликованного коммита
2. Зафиксировать эталон текущего Vinext-приложения: production build, desktop/mobile smoke-тесты главной карты, каталога трасс, Спа, Бахрейна, поиска и 404
3. Создать отдельный Supabase-проект `staging`; production-проект до проверки импорта не создавать
4. Подготовить Supabase-совместимый bootstrap PostGIS и проверить все 17 миграций на пустой базе. Не перестраивать доменную схему и не переносить таблицы в `public`
5. Загрузить только воспроизводимые seed-данные, выполнить `verify-database` и аудиты, затем заново сформировать JSON/GeoJSON read-model
6. Не подключать браузер напрямую к Supabase на первом запуске. Строка подключения хранится только в локальном `.env`/секретах CI; схема `atlas` не публикуется через Data API без отдельного решения и RLS
7. Развернуть текущий Vinext runtime на Cloudflare как первый стабильный preview. Это его штатная цель публикации и самый короткий путь без повторной поломки карт
8. Для Vercel вести отдельную ветку совместимости: сначала параллельные команды `dev:vinext` и `dev:next`, затем исправление типов и карт, визуальное сравнение маршрутов и только после полного паритета смена основной команды сборки
9. После успешного Next.js preview настроить в Vercel корневую папку `apps/web`, проверить динамические маршруты и лишь затем подключить production-домен
10. Автоматизацию обновления сезона строить как отдельный CI-процесс: импорт в Supabase → проверки → экспорт снимков → публикация сайта. Vercel-функции не должны пытаться записывать новые JSON в файловую систему работающего деплоя

Контрольные условия завершения этапа:

- чистое рабочее дерево и однозначный rollback-коммит;
- одинаковое отображение всех карт в dev и production build;
- пустой Supabase staging полностью разворачивается из миграций и seed-файлов;
- браузер не содержит секретов PostgreSQL;
- preview имеет воспроизводимый URL и повторно собирается из Git без ручных исправлений.
