# Туристический слой: пакетный сбор и редакционное одобрение

Цель: готовить для каждой трассы понятный пакет кандидатов, который владелец проекта проверяет группами и исключениями, редактирует при необходимости и сам одобряет к публикации. Не требуется вручную разбирать каждую точку. Автоматический расчёт не удостоверяет существование входа на трассу, проходимость дороги или пригодность точки во время этапа.

## 1. Инвентаризация и правила отбора

1. Использовать уже привязанные к трассам POI, зоны, точки доступа и маршруты как исходную базу, сохраняя их статусы и ручные правки. Сначала составить сводку по трассе и категориям, а не повторно запрашивать весь мир.
2. Зафиксировать категории по сценарию поездки: прибытие, проживание, досуг и необходимые сервисы. Для каждой задать радиус поиска, целевое число и признаки качества. Целевое число — ориентир, а не повод добавлять случайные объекты.
3. Разделять туристическую точку, связь с конкретной трассой, район проживания, проверенный вход/парковку и маршрут. Наличие POI рядом с контуром не означает доступ на автодром.

## 2. Пакетный сбор и нормализация

4. Запускать сбор по одной трассе или небольшой партии. Имеющийся `bulk-import-travel-candidates.mjs` получает объекты OpenStreetMap по группам и сохраняет их кандидатами; журналировать запуск, источник, дату, параметры и сбои отдельных групп. Повторный запуск должен обновлять только импортные кандидаты и не перетирать проверенные записи или ручные названия.
5. Нормализовать координаты, категории, адреса, сайты, часы работы и имена. Для русского названия сначала брать подтверждённое `name:ru` или уже одобренный вариант; исходное официальное имя сохранять. Если автоматический перевод неоднозначен, оставить запись в очереди исключений, а не выдавать догадку за факт. Платный переводческий API не является обязательной зависимостью.
6. Дедуплицировать по внешнему ID, затем искать вероятные дубликаты по имени, категории и близости координат. Сомнительные пары не сливать автоматически: выводить в короткий список на проверку.

## 3. Автоматические проверки и пакет просмотра

7. На уровне всей партии проверять координаты, принадлежность поисковой области, тип, источник, дубликаты, пустые/шаблонные названия, подозрительные расстояния и отсутствие данных, необходимых для конкретной категории. Подсчитать причины отклонения и показать их отдельно.
8. Формировать предпросмотр карты и таблицу по группам: новые, обновлённые, уже проверенные, сомнительные и отклонённые. Для каждого объекта показывать исходное имя, русское имя, источник, категорию, расстояние и причину попадания в пакет. Фильтры и массовое действие должны позволять одобрять однородную группу; спорные записи — править вручную.
9. Не проверять «вручную всё подряд»: просматривать карту на выбросы, сводку по категориям и очередь исключений, затем точечно открывать только сомнительные объекты. Решение и оператор фиксируются в истории импорта/редактирования.

## 4. Маршруты и точки доступа

10. Генерировать предложения по уже выбранным точкам и типу поездки; сохранять только кандидатами с предпросмотром, источниками и воспроизводимым порядком остановок. Для прибытия к автодрому отдельно выбирать и подтверждать вход, парковку или иную конечную точку доступа. Автоматическая близость к трассе не подтверждает доступ.
11. В админке редактировать остановки, линию, конечную точку и условия; карта показывает все привязанные POI, контур трассы и неархивные маршруты для проверки наложений. Изменение существенных данных возвращает маршрут к кандидату для повторной проверки.

## 5. Одобрение, публикация и повторение

12. По итогам пакетного просмотра владелец проекта одобряет выбранные группы/объекты и отдельно спорные маршруты. Импорт не должен сам повышать `candidate` до `reviewed` или `published`; массовое одобрение — явное действие оператора с предпросмотром результата.
13. Перед записью публичных файлов запускать `export-circuit-travel.mjs --check --circuit=ID`, затем штатную синхронизацию только опубликованных данных. Экспорт проверяет GeoJSON до замены файла; независимый `audit-public-travel.mjs` проверяет готовый слой. Ошибка не должна скрываться за сообщением об успешной публикации.
14. Хранить отчёт по каждому запуску: сколько найдено, добавлено, обновлено, сгруппировано в дубликаты, отправлено в исключения, одобрено и опубликовано. Это позволит повторять процесс для остальных трасс без расхода времени на индивидуальный обход тысяч записей.

## Текущее состояние и следующий технический пакет

- Уже есть сбор OSM-кандидатов, четыре группы поиска, ограничение размера партии, сохранение статуса `candidate`, ручной редактор POI, генерация предложений маршрутов, проверка будущего экспортного слоя без записи и аудит опубликованного GeoJSON.
- Ещё нужно сделать единый предварительный отчёт по качеству и дубликатам, очередь исключений, безопасное массовое одобрение с историей решения и повторяемый пакетный запуск для нескольких трасс. Начать с одной тестовой трассы, не публикуя кандидатов автоматически.
- Переводить и подтверждать названия без потери официального оригинала; качество переводов и фактическую пригодность ключевых объектов проверять выборочно и по исключениям.
