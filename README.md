# F1 Geovisual Atlas

Интерактивный географический атлас Formula 1 для выпускной квалификационной работы по направлению «Картография и геоинформатика».

Краткий журнал завершённых этапов и контекст для продолжения: [WORK_LOG.md](WORK_LOG.md).

## Концепция

Центральная задача проекта — показать, как менялась география чемпионата Formula 1 с 1950 года. Пользователь сможет выбрать сезон, увидеть входившие в календарь трассы, последовательность этапов и подробную историю выбранного автодрома.

Проект планируется как образовательное неофициальное приложение для любителей автоспорта. Оно не связано с Formula 1, FIA или командами чемпионата.

## Планируемые возможности

- интерактивный глобус с трассами и маршрутами выбранного сезона;
- временная шкала 1950–2026;
- карточки трасс с геометрией, характеристиками, фактами и историей;
- календарь, результаты и положение участников в выбранном сезоне;
- программно построенные 3D-трассы;
- хронология ключевых событий;
- отдельный экспериментальный режим анализа телеметрии.

## Текущее состояние

Рабочий интерфейс атласа использует подготовленные JSON/GeoJSON. Добавлена
начальная схема PostgreSQL/PostGIS, которая станет основным хранилищем сезонов с
1950 года, исторических конфигураций трасс, результатов, туристических объектов
и 3D-зданий. Старый прототип сохранён как источник данных и идей, но не
рассматривается как архитектурная основа новой версии.

Следующий этап данных — подготовить воспроизводимый импорт исторических сезонов
и экспорт снимков для веб-приложения.

Архитектура базы описана в `database/README.md`, а порядок загрузки и обновления
данных — в `docs/import-pipeline.md`.

## Источники и лицензирование

Перед публикацией необходимо отдельно зафиксировать происхождение каждого набора данных, картографической подложки, изображения, видео и 3D-модели. Материалы телевизионных трансляций используются только как визуальные референсы и не включаются в репозиторий.

Лицензия собственного кода проекта будет выбрана до публичной публикации.

## Локальная загрузка фотографий пилотов

Запустите `pnpm run dev` из `apps/web` на компьютере с настроенными `.env.database.local`, `.env.media.local` и `apps/web/.dev.vars`. Файл и обработка (включая удаление фона, если оно выбрано) остаются на этом компьютере. После подтверждения кадрирования локальный сервер параллельно отправляет оригинал и три WebP-варианта в Supabase Storage, затем защищённым RPC регистрирует фотографию в Supabase PostgreSQL. Ключ `SUPABASE_SERVICE_ROLE_KEY` хранится только в окружении сервера и не передаётся браузеру.

Локальная PostgreSQL получает копию записи для локальной админки и экспорта JSON. Если её обновление не удалось, фотография остаётся сохранённой в Supabase, а админка показывает предупреждение. Публичные JSON-файлы опубликованного сайта пока не пересобираются автоматически после загрузки.

## Обновление сезона Jolpica из опубликованной админки

Кнопка `/admin/seasons` запускает `.github/workflows/season-sync.yml` через серверное действие Cloudflare. GitHub Actions выполняет существующий `scripts/sync-active-season.mjs`: получает полный сезон, проверяет и импортирует его в Supabase, создаёт публичные JSON, проверяет веб-сборку и отправляет изменённые снимки в `main`. Cloudflare публикует новый коммит через подключённую Git-интеграцию. Исходный ответ Jolpica и контрольная сумма сохраняются как артефакт Actions на 90 дней. Админка показывает запуск, а не преждевременное сообщение об успешном импорте; результат нужно смотреть в GitHub Actions.

Повторный запуск обновляет прошедшие этапы того же сезона. Импортёр заменяет только записи с источником `jolpica`; подтверждённые в админке изменения сезона, этапов, сессий, результатов, трасс, пилотов и команд сохраняются. У сезонных записей команды нет собственного источника, поэтому существующее название команды в сезоне импорт не меняет. Актуальные зачёты берутся из Jolpica. Перед первым production-запуском нужно проверить сезон с ручными редакторскими изменениями.

Локальная проверка сохранения ручных правок: `node --env-file=.env.database.local --test scripts/tests/jolpica-repeat-import.test.mjs` из корня репозитория. Тест использует локальную PostgreSQL и откатывает все изменения.

Перед первым использованием настройте:

1. В GitHub Actions репозитория — секреты `SUPABASE_PGHOST`, `SUPABASE_PGPORT`, `SUPABASE_PGDATABASE`, `SUPABASE_PGUSER`, `SUPABASE_PGPASSWORD` для подключения к production Supabase PostgreSQL. Доступ runner к этому адресу и возможность записи в `main` должны быть проверены отдельно.
2. В Cloudflare Worker — секрет `GITHUB_SEASON_SYNC_TOKEN`: токен только для этого репозитория с разрешением GitHub Actions **write**. Он нужен только серверу для запуска workflow; браузеру токен не передаётся. После добавления секрета кнопка станет доступна.
3. Один тестовый запуск через админку: дождаться завершения Actions, проверить результаты аудита, новый коммит и успешный деплой Cloudflare. Если импорт БД завершился, а публикация файлов не удалась, устранить причину в Actions и повторно запустить задачу для того же сезона; обновление должно заново собрать снимки из текущей БД.

Не запускайте импорт одновременно другим способом: workflow сериализует только собственные запуски. Локальные незакоммиченные каталоги пилотов и команд не попадают в Actions и потребуют аккуратного согласования с новым коммитом перед `git pull`.
